# Compact garden with continuous scrolling and flower picker

User direction, 2026-11-26: the current garden is hard to scroll/use. Provide BOTH smooth scrolling and a right-side pop-out icon picker; each flower option contains only its name and picture. Remap/redesign the layout for intuitive scrolling. Thin the near forest while retaining the original front appearance. The subsequent clarification explicitly permits adjacent flowerbeds and non-round shapes: prioritize aesthetic organization in full bloom and ease of use.

This request supersedes0072's fixed-stop-only navigation, mandatory separate round-island composition, and absolute no-near-forest-thinning rule where they conflict. Preserve original house footprint/yaw, rear porch/steps, terrain, lake/shoreline, front architectural identity/entry, far forest and front composition. User-approved exact layout, wording, sprites, shaders and timing discretion in0067/0004 applies. No additional product answer is pending for conservative details in this scope.

## Approach

Use one compact planted garden room with adjacent beds/strips and a gently curved or serpentine main walk. Shape beds to the planting composition; round islands and individual circular soil mounds are not requirements. Compose with mature canonical flower sizes/colors/heights first, then check seedlings and mixed stages. Tall flowers should frame rather than hide shorter blooms. Keep all13 named type zones, meaningful flower groupings, readable direct plant access and rear-house/lake views. Avoid long empty connectors, duplicated13-type expansion loops and huge distance determined by sparse global IDs.

One continuous ordered tour follows the actual main walk. Forward/back scroll advances/reverses the same distance/progress and smoothly composes camera turns. It has clear start/end bounds, with no wrap or teleport at an arbitrary graph junction. Prefer a native vertical scrollport with the world pinned, so mouse wheels, trackpads, touch inertia and keyboard page navigation behave normally. Use one progress authority shared by scroll, picker, actual camera and selected type; do not leave the old selected-stop reconciler competing with scroll state. Renderer and picking use the same exact pose/lens.

The right-edge flower tab opens a compact panel with13 actual flower pictures and names only. Each item navigates to that type's bed on the SAME tour, then closes the panel; it does not submit care, plant or open a flower activity. Use static lightweight portraits of the existing canonical mature flower models, not emoji, private plant content or13 live GPU canvases. Panel rows have no counts, stages, descriptions or care badges. Ordinary focus/selection styling and accessible names are fine. Escape/outside dismissal and selection restore focus appropriately. The panel's own scrolling never moves the world behind it. Keep real flower clicking/seed planting and hidden per-plant keyboard access.

Replace the current Back/current/Onward/native-stop selector and floating route-target chrome in GardenV2. No WASD/pad/arbitrary-ground free walking. Public landing/legacy interactions remain where not superseded. Reduced motion supports immediate scroll/picker positioning without inertial/tween camera motion.

## Layout and data

Make one presentation remap, without rewriting persisted IDs, global spots, seeds, growth, content, history or backend rules. Compact per-type packing can use existing immutable planting metadata (`Flower.planted_at`, ID/spot tie-breaks and seed/model envelope); the builder must specify ordering/stability and tie behavior before implementation. Do not use a huge global spot number as a physical empty-space reservation. Generate work from actual occupied plants plus13 planting targets; new flowers extend beds naturally. Ordinary growth, repeated planting, lower-hole allocation and refresh should not shuffle established plants or reset the view. If this cannot be achieved without a new schema/rule, escalate rather than inventing one.

Every current/new plant and type's planting target must be reachable and usable via the tour and existing accessible plots, including multiple plants/type, sparse12001 and high-address bounded-work cases. Expansion may lengthen/extend beds and the tour using documented stable anchors; preserve the current semantic location when the layout changes rather than blindly retaining an old global percentage. Empty zones remain recognizable and selectable. Frame full-bloom crowded fixtures, not only tiny sprouts.

## Forest and geographic preservation

Use selective static near-forest thinning, preferably obstructing understory/lower foliage/redundant hidden material, to open the rear route and comfortable house views. Preserve prominent front-facing trunks/crowns, silhouette/density, original house/ground/lake/rocks/sun and front entry. Do not globally clear or relocate the forest. One consistent thinned site must serve both views; no camera-dependent fake clearing and no private GardenState driving public geometry. Frozen original factories can remain authority/provenance, but actual allowed thinning must be explicitly documented rather than falsely described as unchanged original GPU output.

Capture the existing original front before editing at the required four sizes and day/dusk/night, including member entry views. Compare actual new front output after thinning under matching conditions, inspect shadows and silhouettes, quantify observed differences and preserve original reference. Do not silently replace the baseline or loosen a guard to bless a materially changed front. If sufficient thinning cannot preserve the front's appearance, escalate the concrete conflict. Show early actual front/rear and full-bloom garden/scroll prototypes before broad final verification, so failed composition does not consume repeated full runs.
